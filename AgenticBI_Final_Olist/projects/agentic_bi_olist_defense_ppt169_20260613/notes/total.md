# 01_cover
各位老师、同学大家好，我们小组的项目是基于巴西 Olist 电商数据集的 Agentic BI 分析系统。
我负责成员 D 的最终整合部分，今天会从项目目标、系统架构、核心能力、演示逻辑和最终交付五个角度进行汇报。

---

# 02_defense_roadmap
这次答辩我会先说明业务问题和整体方案，再介绍数据层、预聚合层和多 Agent 编排。
中间部分重点展示系统如何回答描述性、诊断型和策略型问题，最后总结项目复盘、后续计划和提交材料。

---

# 03_problem_framing
传统 BI 看板适合固定指标监控，但业务同学经常会继续追问原因、对比和行动建议。
所以我们的目标不是只做一个图表页面，而是让用户用自然语言完成从提问到分析结果的闭环。

---

# 04_system_architecture
系统整体分成四层：底层是 Olist 原始数据和 SQLite 数据库，中间是预聚合视图，上层是多个 Agent 的任务协作，最外层是 Streamlit Web 交互。
这种设计让复杂问题可以被拆成 SQL 查询、结果解释、图表生成和上下文记忆等子任务。

---

# 05_data_pipeline
数据层先把九张原始表清洗入库，再针对高频业务问题建立预聚合视图。
这样既保留了明细数据的追溯能力，也让常见分析问题可以更快返回结果，为现场演示提供稳定基础。

---

# 06_preaggregation_benchmark
性能优化是项目里非常关键的一步，直接查询明细表时，多表关联会明显拖慢响应。
我们把月度 GMV、州别销售、配送表现等指标沉淀为视图后，典型查询获得了数量级上的加速，这也是系统能够支持交互式问答的原因之一。

---

# 07_agent_orchestration
多 Agent 部分由 Coordinator 统一接收用户问题，再根据意图路由到 SQL Agent、Visualization Agent、Insight Agent 或其他工具。
这样做的好处是每个 Agent 只处理自己擅长的任务，同时共享状态里会记录问题、结果和生成资产。

---

# 08_memory_followup
在真实使用中，用户很少只问一个孤立问题，常见情况是先问整体，再追问某个州、某个品类或某种支付方式。
因此系统加入了 MemorySaver 和显式历史，把上一轮问题、SQL、结果摘要和图表路径保留下来，让后续追问不会丢上下文。

---

# 09_demo_script
现场演示设计成三类问题：第一类是描述性分析，证明系统能快速概览经营现状。
第二类是诊断型分析，证明系统能解释问题背后的原因；第三类是策略型分析，用来展示 What-if 和异常检测等扩展能力。

---

# 10_descriptive_demo
这一页对应描述性问题，例如“各州销售额如何分布”或“哪些州贡献最高 GMV”。
系统会优先命中州级销售视图，返回图表和解释，帮助用户从宏观层面快速识别重点市场。

---

# 11_payment_behavior
支付热力图展示的是支付方式和分期期数之间的关系。
从业务解释上看，信用卡和分期是 Olist 场景里的核心支付行为，因此后续可以围绕高客单价品类设计分期营销策略。

---

# 12_diagnostic_demo
诊断型问题关注的不只是结果，而是为什么会出现某类异常。
以配送时效为例，系统先定位延迟天数分布，再联动卖家、州别和品类字段，最终把发现转化为运营干预建议。

---

# 13_review_category_insight
评分和品类热力图帮助我们判断哪些品类更容易引发低评分。
答辩时我会强调，这类图表不只是展示满意度，还能指导客服、履约和卖家治理的优先级排序。

---

# 14_bonus_capabilities
在基础问答之外，系统还保留了 What-if 推演和异常检测两类加分能力。
What-if 用来回答策略变化可能带来的影响，异常检测则把延迟、运费或评分里的异常点作为下一轮追问入口。

---

# 15_visualization_coverage
这页汇总了系统目前覆盖的主要可视化类型，包括州别 GMV、品类销售、区域客单价和物流成本关系。
不同图形对应不同业务视角，说明 Dashboard Agent 能根据问题选择合适表达方式，而不是固定输出同一种图表。

---

# 16_challenges_fixes
项目过程中主要遇到三个挑战：明细查询慢、自然语言问题有歧义、图表输出需要可控。
对应的处理方式分别是预聚合视图、Coordinator 状态编排和 Visualization Agent 规则化输出，这些修正让系统更稳定、也更容易复现。

---

# 17_three_month_actions
如果继续迭代，我们计划分三个月推进：第一个月完善数据刷新和质量检查，第二个月强化意图识别和失败回退，第三个月把分析建议沉淀为业务任务和复盘指标。
最终目标是让业务同学用自然语言完成发现、解释、行动和复盘的完整链路。

---
